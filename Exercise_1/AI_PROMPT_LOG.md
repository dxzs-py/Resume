# AI Prompt 与问题解决记录

本文档记录本项目开发过程中使用的 Prompt 设计与关键问题的解决过程。

## 一、System Prompt 设计（`agent/prompts.py`）

```
你是一个可通过工具获取外部信息的智能助手。

【工具使用策略】
1. 涉及数学运算必须调用 calculator 工具精确计算，不要心算；
2. 需要查资料、事实或概念时用 search 工具；
3. 查天气用 weather 工具；
4. 常识问答、闲聊、写作、翻译类任务直接回答，不必调用工具。

【多步任务指引】
复杂任务可连续调用多个工具：每次拿到工具结果后判断信息是否足够，再决定下一步动作；全部信息齐备后再给最终回答。调用工具前先用一句话说明思路。

【失败处理】
工具返回 Error 时，阅读错误信息，调整参数或换方法重试；同一失败的调用不要原样重复。

【回答规范】
基于工具结果作答，不编造数据；工具查不到就如实说明；回答简洁、结构化；不向用户暴露内部工具协议细节。
```

设计意图：

1. **工具使用策略逐工具列举**——三个工具各给一条明确的触发条件，并显式给出"直接回答"的反例，降低模型乱调工具率；
2. **"不要心算"**——LLM 算术容易出错，强制数学运算走 calculator，这是工具价值最直接的体现；
3. **多步任务指引**——引导模型在拿到工具结果后继续循环而不是提前作答，同时要求先说思路（对应解析器把 content 解析为 thought）；
4. **失败处理**——与 runtime 的"错误回传"机制配套：错误文本进入上下文后，这段指令让模型把 Error 当线索自我纠正，而不是原样重试或放弃。

工具自身描述（description）同样按"给 LLM 看"的标准撰写，例如 calculator 描述中写明"任何算术运算都必须使用此工具，避免心算误差"。

## 二、问题解决记录

### 问题 1：tool_calls 与 tool 消息的配对协议（400 错误）

- **现象**：早期直接把工具结果作为普通 assistant 消息追加，下一次 LLM 请求报 400。
- **原因**：OpenAI 兼容协议要求 assistant 消息中的每个 `tool_call` 必须有一条携带对应 `tool_call_id` 的 `role="tool"` 消息配对，缺失即校验失败。
- **解决**：runtime 在每个工具执行后立即以 `role="tool"` 回填；`store.save` 只放在循环收尾（消息序列必然合法的时刻），保证落盘文件可被 `--resume` 安全重放。中途若 LLM 调用抛错，发生在写 assistant 消息之前，session 不会留下未配对消息。

### 问题 2：滑动窗口截断切断 tool 配对（本次修复）

- **现象**：历史超过阈值触发滑动窗口压缩时，若切分点恰好落在 `assistant(tool_calls)` 与其 `role="tool"` 结果之间，窗口开头会出现"孤儿 tool 消息"，恢复后再次请求报 400。
- **解决**：`ContextManager.build_messages` 在按 `keep_recent` 切分后，把窗口起点回退到第一条非 `role="tool"` 的消息处（配对消息在 session 中总是相邻写入，回退即可保住完整配对），并增加回归测试 `test_window_never_starts_with_orphan_tool_message`。

### 问题 3：工具失败导致整轮循环崩溃

- **原因**：若工具异常直接向上抛，一次缺参就中断整个 Agent 任务。
- **解决**：确立"错误回传而非中断"策略——`ToolRegistry.execute` 永不抛业务异常，失败包装为 `"Error: ..."` 字符串回传；LLM 幻觉出的未注册工具名由 runtime 单独捕获 `ToolNotFoundError` 后同样回传错误文本。模型可据此补参/改名重试。配套在 System Prompt 中写明失败处理策略。

### 问题 4：calculator 安全性

- **原因**：LLM 生成的表达式直接 `eval` 等于把任意代码执行权交给模型输出。
- **解决**：基于 `ast.parse` + 白名单求值：只放行数字字面量、七种二元运算、一元正负号、函数白名单（sqrt/log/sin/…）、常量白名单（pi/e）；拒绝属性访问、字符串、容器字面量、关键字参数。测试覆盖 `__import__`、`__class__` 等攻击形态。

### 问题 5：迭代失控风险

- **原因**：LLM 可能陷入"反复调工具-永远不满意"的循环，无限烧 token。
- **解决**：`max_iterations` 硬上限（默认 8，可配置），for-else 语法区分"正常 break"与"轮次耗尽"，耗尽时返回明确系统提示并记录 trace 事件。

### 问题 6：LLM 网络故障与重试策略

- **解决**：仅对暂时性错误（超时/连接失败/429）按 2^n 秒指数退避重试；401/400 等确定性错误立即失败，避免无意义等待。依据：chat 调用幂等无副作用，重试安全。

### 问题 7：多窗口会话隔离与持久化方案选型

- **对比**：单文件全量存储（读放大、易整体损坏）、SQLite（引入部署依赖）、每会话一个 JSON 文件（隔离、可读、零依赖）。
- **选择**：每会话一个 JSON 文件。单文件损坏不波及其他会话；按 `session_id` 直读恢复，无需索引；`list_sessions` 对损坏文件跳过并告警，做到部分容错。
